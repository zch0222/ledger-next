# 自主交付授权与自评估规则

记录日期：2026-10-02（Asia/Hong_Kong）· 记录人：Claude Code · 适用范围：M1-AUTH 起至 M7 的全部开发任务。

## 用户授权原文

> 切换到最新的main分支按照里程碑文档继续后续的开发直到完成所有里程碑待办，遇到里程碑或者方案文档中提到的门禁、需要人工审查的部分你自己进行评估进行e2e测试，评估修改没问题之后继续后续开发，跳过人工审查。人工审查在所有东西开发完成后进行。开发过程中要及时更新进度，使用docker进行e2e验证单元测试覆盖。遇到消息通知等需要连接第三方服务的，进行本地mock，不要连接真实的服务器。

## 执行规则

1. **自评估代替逐项人工签署**：需要评审的任务由实现者按执行卡的验收标准逐条核对，以本机 Docker 端到端测试（`pnpm test:e2e`）、MySQL 集成测试和单元测试为依据。通过后用 `--review-mode self` 标记 done；`milestones.json` 中的 `reviewMode: "self"` 表示“自评估完成，待最终人工审查”，不是独立人工验收。
2. **最终人工审查**：所有自评估任务及其 `finalChecks`（需要人工或真实环境确认的事项）汇总在 [MILESTONES.md](../MILESTONES.md) 文末“最终人工审查清单”。人工审查不通过时，应把相应任务退回 in_review 并处理受影响的后续任务。
3. **G1 不自评估**：发布验收 G1 必须由真实发布负责人签署；`progress.mjs` 拒绝以 self 模式完成 G 开头的门禁任务。
4. **第三方服务一律本地 mock**：汇率供应商、Telegram、飞书、企业微信、pushplus（个人微信）、SMTP、外部 Webhook 接收端，以及四个 Agent 客户端所依赖的模型服务，均不连接真实服务器。Docker 测试栈内运行协议级 mock（`apps/mock-services`），按各供应商公开文档的请求 / 响应格式实现，并可注入 429、5xx、超时、凭据错误等故障。
5. **真实联调保留为人工审查项**：方案中“真实接收证据”“真实客户端联调”等验收项，在自评估阶段以 mock 协议测试代替并明确标注；它们作为 `finalChecks` 进入最终人工审查，不宣称已经在真实渠道验证。
6. **证据**：每个任务的 `docs/evidence/{task-id}/README.md` 写明日期、执行命令、实际结果、mock 范围和已知限制。运行时生成的报告、trace、随机测试账号不入 Git。

## 环境说明

本次开发在云端容器中进行：Docker Engine 29 本机守护进程，Node 24.21 / pnpm 11.19.0。容器出站 TLS 经代理重签，镜像构建通过 BuildKit secret `build_ca`（`LEDGER_BUILD_CA`，见 `compose.build-ca.yaml`）临时信任代理 CA；CA 不进入镜像层，生产构建不需要该设置。
